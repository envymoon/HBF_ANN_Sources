# 02 · 图 ANN 与外存 I/O：从 DiskANN 到 PipeANN

## 1. 图 ANN 是怎么搜的（Best-First / Beam Search）

```
候选队列 = {入口点}
重复：
   取出队列里离 query 最近、且还没展开的节点 u
   读 u 的邻居列表 (+ 原始向量)           ← 一次存储访问
   对每个邻居 v 计算距离，放入候选队列
直到没有更近的候选
```

- **每一跳都依赖上一跳的结果**：要先读到 u 的邻居列表，才知道下一步去哪。这就是**指针追逐 (pointer chasing)**。
- 一次查询通常要走几十到上百跳，访问路径完全**由数据决定**，也**无法提前知道**。

对比 **IVF-PQ**：先做粗量化，选出 nprobe 个簇，之后要扫描的所有地址**一次就全部确定**。可以把每个簇的数据条带化铺满所有 channel，一次全部发出，带宽很容易打满（HAVEN 就是这样把 IVF-PQ + rerank 放到 HBF 上的）。
**图算法做不到“一次全部确定”，这是一切困难的起点。**

## 2. 搬到外存时的标准做法（DiskANN 范式）

DiskANN（NeurIPS'19）定下的基本框架，后续工作都沿用：

| 放在哪 | 存什么 |
|---|---|
| 内存（对应我们的 HBM） | 所有向量的 **PQ 压缩码**，用于快速估算距离并决定下一步读谁；入口点和热点节点缓存 |
| 磁盘（对应我们的 HBF） | 每个节点一条记录：**原始向量 + 邻居 ID 列表**，按 4 KiB 页对齐 |

- 搜索时每一跳读出 **W 个**最好的候选（beam width），一跳完成后再发起下一跳，即**同步 beam search**。
- 每次 I/O 读回一整页：当前节点的邻居列表用来扩展，原始向量用来精确重排。

## 3. 两条优化路线（正好对应你的两个问题）

### 路线 A：布局（Layout）：减少 I/O 次数 → 对应问题 1

核心思想：**把经常一起访问的节点放进同一页**，一次读页就能顺带拿到“下一步大概率要用的邻居”。

| 工作 | 做法 |
|---|---|
| DiskANN 默认 | 按 ID 连续放，16 个节点一页，几乎没有局部性 |
| **Starling** (SIGMOD'24) | **Block shuffling**：重排节点，最大化“页内邻居重叠率 (overlap ratio)”。论文证明这个问题是 NP-hard，给出启发式算法 BNP/BNF/BNS，推荐 BNF |
| DiskANN++ | 用 star/bin packing 把图上靠近的节点打包到同一页 |
| MARGO | 按“单调搜索路径”来优化布局，选择保留哪些边 |
| **PageANN** (2025) | 直接把**一页当作一个图节点**，页内放向量、邻居 ID 和邻居的压缩向量，一跳只需一次读页 |

> 这些方法的**优化目标都是“读页次数最少”**，背后的假设是 SSD 的代价模型：**一次读页 = 一个固定成本，与读的是哪一页、在哪个位置无关**（SSD 内部的 FTL 会帮你打散到各个 die）。

### 路线 B：并发/流水：掩盖延迟 → 对应问题 2

| 工作 | 做法 |
|---|---|
| DiskANN | 同步 beam：每跳 W 个请求，**全部返回后**才进入下一跳。等待时 SSD 空闲 |
| **PipeANN** (OSDI'25) | **打破 best-first 的严格顺序**：不等一跳的全部 I/O 返回，只要有结果回来就立刻计算，同时持续发出新请求，让 SSD 队列始终保持满载。代价是部分请求是“猜”的，可能白读。结果：延迟只有 DiskANN 的 35%，是内存版 Vamana 的 1.14 到 2.02 倍 |

> PipeANN 在 SSD 上**只需要决定两件事：什么时候发 I/O、发多少**。SSD 内部会处理放到哪个 die、按什么顺序执行。

## 4. 黄金要点

1. 图 ANN = 指针追逐。**下一步读谁要等这一步读完才知道**，所以很难提前发大量请求。
2. SSD 时代的两类优化：**布局**（减少读页次数）和**流水**（掩盖等待）。
3. 两类优化都建立在 **SSD 把物理细节藏起来**的前提上：读页成本固定，内部并行由 FTL 处理。
4. **HBF 把物理细节暴露出来了**：页缓冲只有 2 个，bank 内串行，channel 和 bank 的分布影响完成时间。所以这两类方法搬过来以后都会“失配”。详见 `03_两个难题根因分析.md`。
