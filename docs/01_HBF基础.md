# 01 · HBF 基础：它是什么、内部怎么组织、为什么离不开 prefetch

## 1. 一句话定位

**HBF（High-Bandwidth Flash）把 3D NAND 像 HBM 一样堆叠起来，和 GPU/xPU 封装在同一个 package 里，通过 UCIe 连接。它的容量约是 HBM 的 8 倍以上，带宽接近 HBM，但读延迟比 HBM 慢约两个数量级。** ✅（HBFSim §1–2）

它是 HBM 之下新增的一层存储，**不能替代 HBM**。

```
            延迟            带宽/栈          容量/栈
HBM4      10–100 ns       ~2 TB/s          64 GB
HBF       ~µs 到 ~20 µs    0.4–3.0 TB/s     512 GB      ← 带宽同一量级，延迟差约 100 倍
SSD       10–100 µs       14–28 GB/s       ~2 TB/盘
```

（数据来自 HBFSim Table 1 ✅。HBF 的 tR 在不同论文里取 1 µs、3 µs、4 µs、20 µs 都有，规范本身没有给出时间参数 🟡，所以下文计算一律按“几 µs 到 20 µs”这个区间来做。）

规范进展：2026-08 Sandisk 与 SK hynix 通过 OCP 发布了第一版规范（v0.7.0）。它定义了 8-hi 和 16-hi 两种堆叠，每栈最大 512 GB，带宽分 3 档（0.4 到 3.0 TB/s），互连采用 UCIe。第一批样品预计 2027 年出。✅

## 2. 内部层级：从“栈”到“页”

对应附图 `assets/hbf_cube_4ch.png`（图里只画了 4 条 channel，规范是 16 条）。

```
HBF 栈 (cube)
 └─ Host Channel × 16        ← 每条 channel 有独立的 UCIe 全双工数据通路，彼此独立、互不访问 🟡
     └─ Die (NAND 芯片层)
         └─ Bank             ← 一次只能做一件 sense；同一 bank 内的 sense 按顺序执行 🟡
             └─ Plane        ← 真正做“感测(sense)”的单元，一次 sense 读出一整页 (4 KiB)
                 └─ Page Cache / Page Buffer × 2（每个 bank 2 个 4 KiB 缓冲） 🟡
```

**关键规则（都在这里，务必记住）：**

| 规则 | 含义 | 来源 |
|---|---|---|
| **sense 粒度 = 4 KiB 页** | 不管你要多少字节，NAND 都得把整页读到 page buffer，耗时 tR | ✅ NAND 物理特性 |
| **传输粒度 = 64 B** | 页已经在 buffer 里时，可以按 64 B 的倍数（64 B 到 4 KiB）取走，取数不能跨越 4 KiB 页边界 | 🟡 OCP 规范 burst 规则 |
| **每个 bank 只有 2 个页缓冲** | 页还在 buffer 里，再读它就**不用重新 sense**（命中）；buffer 被别的页挤掉后，再读就要再付一次 tR | 🟡 (HBF Sucks? 引用规范 §5.3；HBF-EventLab 按此实现) |
| **bank 内顺序感测** | 同一 bank 的多个 sense 请求只能排队，**不能并行** | 🟡 |
| **写必须攒满 4 KiB** | 写入以整页为单位，而且会消耗 P/E 寿命 | 🟡 规范 §5.4 |

> 💡 **与 SSD 最本质的区别**：SSD 前面有 FTL 和控制器，把物理位置和内部并行度全部藏起来，主机只看得到一个平坦的 LBA 空间，读取单位是 4 KiB。HBF 的读取单位缩小到 64 B，channel 和 bank 层级离软件近得多，**“读哪一页、在哪个 bank、按什么顺序读”这些以前由 SSD 内部处理的事，现在要由系统软件或算法来决定**。这正是你那两个难题出现的根源。
>
> ❓ 需要在 OCP 规范原文里确认：地址到 (channel, die, bank, plane) 的映射是固定的（软件可见），还是由 base die 控制器做交织或重映射？这一点决定了“布局能不能直接控制 bank 分布”。

## 3. 为什么 HBF 必须 prefetch：用 Little 定律算一笔账

**Little 定律：带宽 = 在途数据量 ÷ 延迟。** 要想跑满带宽，必须同时“挂起”足够多的请求。

| | 目标带宽 | 延迟 | 需要的在途数据量 | 折算成 4 KiB 页 |
|---|---|---|---|---|
| HBM | 2 TB/s | 100 ns | **200 KB** | ~50 |
| HBF (乐观) | 3 TB/s | 4 µs | **12 MB** | ~3,000 |
| HBF (保守) | 3 TB/s | 20 µs | **60 MB** | ~15,000 |

**结论：HBF 需要在途的请求数是 HBM 的 60 到 300 倍。** GPU 靠 warp 切换掩盖延迟，这种机制只够应付 HBM 级别的几百纳秒；面对几十微秒，单靠“发出 load 后就地等待”，带宽会被延迟限制，只能用到一小部分。

换个角度，从 NAND 内部看：

```
单个 plane 的读带宽 ≈ 4 KiB / tR
  tR = 4 µs   → ~1 GB/s
  tR = 20 µs  → ~0.2 GB/s
要到 3 TB/s → 需要约 3,000 到 15,000 个 plane/bank 同时在感测
```

所以说 **HBF 的高带宽是用海量并行“拼”出来的，单个单元其实很慢**。想拿到这部分带宽，必须同时满足两件事：
1. **提前知道**要读哪些地址（这就是 prefetch，也就是提前发出请求）；
2. 这些地址要**均匀分散**到各个 channel/bank 上（不然就在少数 bank 上排队）。

### 为什么 prefetch 在 LLM 场景里“出现频率很高”

所有 HBF+LLM 论文（HBFSim、FlashAccel、FLINT、HBFlex 等）都把 prefetch 作为核心机制，原因是 LLM 的访问序列**可以预测**：

- Transformer 逐层执行，第 i 层算完就是第 i+1 层；需要哪些权重**事先完全确定**。
- HBFSim 在 H100 上算过：计算第 i 层大约需要 **130 µs**，读第 i+1 层权重只需约 20 µs，计算时间是读取时间的 **6.5 倍**，所以延迟完全可以被计算掩盖。✅
- 也就是说，**HBF 能用在 LLM 上，前提就是 prefetch 能掩盖延迟**。

**但有一个反例，和图 ANN 非常像：MoE。** 选哪个 expert，要等上一层算出结果才知道，访问顺序变成了运行时才确定。HBFSim D6 的做法是根据已经发生的访问去“猜”后续页（推测式 prefetch）：在合成 MoE 流上，不需要等 media 的访问比例从 18% 提到 89%，代价是总读取量多了约 16.5%（猜错的读）。✅
→ **这正是图 ANN 将要面对的局面：访问由数据决定，只能靠推测来 prefetch。**

## 4. HBF 的另外几个约束（做设计时别踩坑）

1. **怕写**：写是整页写，耗寿命，而且比读贵得多。HBF 适合“一次写入、多次读取”的数据。✅
   - 《HBF Sucks?》的结论：把 HBF 当 SSD 用来做 KV 卸载反而更慢，因为这种负载写多读少。HBF 生效的三个条件是：在关键路径上、写入能被后续读取摊销、带宽可持续。🟡
   - **对我们是好消息**：ANN 索引基本是只读的，天然契合 HBF。索引更新的写入问题可以作为后续议题。
2. **温度会限制带宽**：同一个 package 里 GPU、HBM、HBF 一起发热，标称带宽不等于持续带宽。HBFSim 的结果显示先到热上限的是计算 die，不是 HBF。✅
3. **retention/refresh**：温度越高，数据保持时间越短，需要后台刷新，刷新会占用前台读带宽。✅

## 5. 本节“黄金要点”（30 秒版）

1. HBF = NAND 堆在 GPU 旁边：**容量大、带宽高、延迟高（µs 级）、怕写**。
2. 高带宽 = **大量慢单元同时工作**。要吃满带宽，就要**提前发出数千到上万个请求，并且分散到所有 channel/bank**。
3. 感测按 4 KiB 页，传输按 64 B；每个 bank 只有 2 个页缓冲，bank 内必须串行。
4. LLM 的访问可预测，prefetch 天然成立；**图 ANN 的访问不可预测，就像 MoE 一样，这是我们问题的起点**。
