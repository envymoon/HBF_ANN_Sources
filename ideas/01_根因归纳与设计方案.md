## 0. 先用一个代价模型把两个问题统一起来 🧮

两个问题表面上一个是“空间”（放在哪）、一个是“时间”（按什么顺序发），但它们都落在同一个公式上。

**吞吐上限**（每栈）：
```
QPS ≤ (U / tR) × u × η / S

U   = 能同时感测的单元数（bank/plane），≈ 256–1024/栈          ✅ OCP（数字不一致，需扫描）
tR  = 一次页感测时间，1–20 µs                                   ✅ 规范没给
u   = bank 时间利用率：有多少 bank 时间在做“有用的 sense”         ← 被冲突、热点、空等、白读压低
η   = sense 有效率：每次 sense 平均用上几个“有用节点”               ← 由布局和“读出时机”决定
S   = 每个查询需要的有用节点数（≈ 跳数 × 每跳展开数）               ← 由图算法、缓存决定
```
**延迟下限**：
```
Latency ≥ 跳数 × (tR + 平均 bank 排队时间)
```

把两个问题放进去：
| | 压低的是哪一项 | 机制 |
|---|---|---|
| 问题 1（页局部性 vs bank 并行） | **η** 和 **u** 互相拉扯 | 节点挤到同一页 → η 高，但读同一批页的请求集中到少数 bank → u 低；节点打散 → u 高，η 低 |
| 问题 2（发多少 + 按什么顺序发） | **u** 和**延迟** | 推测读占 bank 时间（u 里掺了白读）；同 bank 保序造成队头阻塞（排队时间进关键路径） |
| 两者的耦合 | 为了 u 必须高并发 → 高并发冲掉页缓冲（η 降）、加剧 bank 冲突（u 降） | ✅ docs/03 §2.2 根因 ④ |

算个数（U=1024、tR=4 µs、S=100、η=1、u=1）：上限 ≈ **256 万 QPS/栈**。现实里 η、u 都远小于 1，**我们的工作就是把 η 和 u 拉回来，同时不让 S 和跳数变大。**

## 1. 根因再归纳：五个“SSD 时代的默认假设”，在 HBF 上全部失效

这是我读完 DiskANN 原文后最清楚的一点：SSD 上的图 ANN 方法建立在几条**隐含假设**上，HBF 把它们一条条打破了。

| # | SSD 上的默认假设 | 出处 | HBF 上为什么不成立 | 影响哪一项 |
|---|---|---|---|---|
| A1 | “并发读 W 个随机扇区 ≈ 读 1 个的时间” | ✅ DiskANN §3.3 原话 | 并行度暴露给软件，W 个读撞同一 bank 就串行。W=8 在 64 bank 上撞车概率约 37% | u、延迟 |
| A2 | “读进来的 4 KB 在主机内存里想留多久都行” | ✅ DiskANN §3.5、Starling | 只有 sense 是 4 KB；页留在 bank 的 2 个缓冲里，高并发下几乎立刻被挤掉 | η |
| A3 | “页放在哪个物理位置由 FTL 管，布局只管哪些节点同页” | ✅ Starling OR(G) 只统计页内邻居 | **页号直接决定 bank**（`bank = 页号 mod 16`），布局不管 bank = bank 随机分配 | u |
| A4 | “请求顺序设备会自己调度，主机只管发多少” | ✅ PipeANN 只控制何时发、发多少 | **同 bank sense 严格保序、发出后不重排**，主机不排序就会队头阻塞 | 延迟、u |
| A5 | “白读的代价是带宽” | ✅ PipeANN §4.2 | 带宽充裕，白读的代价变成**占 bank 一个 tR + 挤掉页缓冲 + 能耗（2–4× HBM）** | u |

**一句话的根因**：
> SSD 用 FTL 和主机 DRAM 把“设备内部并行结构”和“读出的数据的生存期”都替软件管了；HBF 把这两件事交还给了软件，而现有图 ANN 方法从没管过它们。

还有一个结构性根因，不是假设失效，而是**图搜索本身的性质**：
- **依赖链（pointer chasing）**：下一跳读什么要等这一跳读完（✅ DiskANN Alg.1）。所以单查询在途量最多 W 个，约 8 GB/s，离 TB/s 差两个数量级；**吞吐只能靠多查询并发**，而多查询并发正是 A2、A3 恶化的原因。

## 2. 我认为最重要的四个洞察（讨论的起点）

### 洞察 1：页缓冲靠不住，局部性要在“sense 的那一刻”收割 💡
- 依赖“下一跳再来读时页还在缓冲里”是不现实的（A2）。
- 但有一个时刻**一定命中**：sense 刚完成，紧接着发的同页请求。规范建议“先读完第一页再发第三个地址”，所以**同页请求背靠背发出**就能保证命中（✅ OCP §5.3.1）。
- 做法（暂称 **sense-time harvesting**）：读节点 v 所在页 P 时，在同一批里顺带取走 P 中**其他可能有用的节点**（例如是 v 的邻居、或 PQ 距离足够近的点），按 64 B 粒度只取需要的部分，放进 HBM 的查询私有缓冲。
- 这样 Starling 式的 co-location 收益**不再依赖页缓冲的存活时间**，只依赖“一页里放了多少下一步可能用到的节点”。
- 和 Starling 的“block search”是同一个想法，区别是 HBF 允许 64 B 粒度挑着取，不必把整页搬回来。

**值不值得把整页都搬回来？** 🧮 名义带宽 = U × 4 KB / tR，恰好等于“每次 sense 都搬整页”的带宽。所以**在 sense 速率是瓶颈时，搬整页不会额外占 HBF 带宽**；代价在 HBM 写带宽、HBM 容量和能耗上。如果带宽档位低（0.384 TB/s 档），sense 能力超过链路，这时 64 B 挑着取才真正有用。→ 这是一个要实验的取舍。

### 洞察 2：主机必须“握住”请求队列，只给每个 bank 喂 1–2 个 💡
- 设备里同 bank 严格保序（A4），**请求一旦发出就失去控制**。
- 所以调度要放在主机侧（或者 base die 上的近存逻辑）：**每个 bank 一个主机侧队列，只在 bank 空出槽位时才发**，在途深度限制在 1–2（正好对应 2 个页缓冲）。
- 好处一次拿到三个：
  1. **优先级真正生效**：关键读永远插在推测读前面（解决队头阻塞）；
  2. **页缓冲不被乱序挤掉**：同页请求由主机合并后背靠背发；
  3. **负载均衡有了“选择权”**：见洞察 3。
- 代价：每秒要做上亿次调度决策（🧮 256 M sense/s/栈）。GPU 上做是否来得及、要不要下沉到 base die，是系统设计的关键问题。

### 洞察 3：推测读只填“空闲 bank 时间”，就不再有浪费问题 💡
- PipeANN 的困境是：W 大则白读多，W 小则流水断（✅ PipeANN：W=32 的 I/O 是 W=8 的 2.44 倍）。
- 在洞察 2 的主机侧队列下，可以把请求分成**两个优先级**：关键读（当前最优候选）和推测读（候选列表靠后的、或多跳预测的）。**推测读只在某个 bank 没有关键读可发时才发**。
- 结果：
  - 低负载时 bank 闲着，推测读免费，延迟降低；
  - 高负载时推测读自动让路，不抢吞吐；
  - **W 不需要手调**，由 bank 的空闲程度自然决定（PipeANN 的“探索一个发一个”是在设备不可控时的近似）。
- 剩下的唯一代价是能耗（✅ Characterizing HBF：读能耗 2–4× HBM），可以设上限。

### 洞察 4：把搜索拆成“小数据的指针追逐” + “大数据的批量重排” 💡
- 关键事实（✅ DiskANN §3.1）：**DiskANN 的遍历本来就只用内存里的 PQ 距离引导**，全精度向量只用于最后重排；它把向量和邻接表放在一起，只是因为 SSD 上“顺带读”免费（A2）。
- 在 HBF 上可以改成 **decoupled 布局**（✅ 评测论文：高维时 decoupled 更好）：
  - **遍历阶段**只读邻接表（R=64 时 256 B），一页能放 ~16 个节点的邻接表 → η 天然高、跳数不变；
  - **重排阶段**一次性读 top-K 候选的全精度向量。**这些 ID 是一次全部已知、互相无依赖的**，正是 HAVEN/IVF 那种“HBF 友好”的访问，可以完美打散到所有 bank。
- 这把问题的难点**缩小到“邻接表的指针追逐”**这一块，数据量少一个数量级，更容易放进 HBM/SRAM 做缓存或副本。

## 3. 设计空间：一个分层架构草图 💡

```
                ┌──────────────────────── GPU / Host ─────────────────────────┐
                │  批量查询（N≈100–1000/栈）  → 每个查询的候选表 + PQ 距离（HBM） │
                │                                                               │
                │  ① Bank 感知调度器                                             │
                │     - 每 bank 一个队列，在途 ≤ 2（credit）                       │
                │     - 优先级：关键读 > 重排读 > 推测读                            │
                │     - 同页合并 + sense-time harvesting                         │
                │     - 副本选择：挑负载轻的 bank（power of two choices）           │
                │     - Batch Read 提示：一批无冲突请求立即下发                     │
                └──────────────────────────────┬────────────────────────────────┘
  HBM（几十 GB）: PQ 码、上层导航图、入口邻域缓存、查询状态、收割回来的节点
                                               │
  Base die SRAM（~MB 级/栈）: 最热邻接表页 / 热点页副本（同时躲开读干扰）
                                               │
  HBF（数百 GB/栈）
     ├─ 邻接表区（decoupled，紧凑）：页内放图上相近的节点（提高 η）
     │                             页号按“同轮共现”着色分 bank（提高 u）
     │                             热点页 2–k 副本，分布在不同 bank
     └─ 向量区：全精度向量，只在最后重排时批量读
```

各部件对应解决的根因：
| 部件 | 解决 | 借鉴自 | 新在哪里 |
|---|---|---|---|
| 上层/热点放 HBM、SRAM | 热点 bank、读干扰、前几跳延迟 | ✅ Starling 内存导航图、DiskANN C 跳缓存、HBFlex SRAM 卸载 | 把**读干扰**也作为放置依据 |
| Decoupled 布局 | η、把难点缩小 | ✅ 评测论文 | 重排阶段变成 HAVEN 式无依赖批量读 |
| 页内 co-location + harvesting | η（A2） | ✅ Starling | 不依赖页缓冲存活，按 64 B 挑着取 |
| 页号着色分 bank | u（A3） | ✅ HBFlex plane group | 图 ANN 上没人做过；利用 OCP 确定映射 |
| 热点副本 + 选副本 | u（热点、冲突） | ✅ HBFlex 前缀副本 | “两个选择”理论保证：最大负载从 log n/log log n 降到 log log n |
| 主机侧 bank 队列 + 优先级 | 延迟、u（A4、A5） | — | PipeANN 在 SSD 上做不到（设备不可控） |
| 推测读只填空闲 | u、W 自适应 | ✅ PipeANN、HBFSim D6 | 用 bank 空闲度代替手调 W |

## 4. 需要讨论、或必须用实验回答的取舍

1. **静态布局（着色）和动态调度（选副本、重排队列）哪个更值？** 如果调度已经能把冲突消掉大半，布局着色的收益可能很小，反之亦然。→ 要分别开关做消融实验。
2. **η 和 u 的取舍**：co-location 越强，热门页越集中，读那几页的 bank 越忙。副本数 k 该随“页热度”变化，而热度来自查询分布，需要 trace。
3. **调度放在哪**：GPU 上做（灵活，但每秒上亿次决策、跨 UCIe 有延迟）还是 base die 上做（离 bank 近，但要改硬件/固件，规范里 base die 的调度是产品决定的）？这决定了研究偏“软件”还是偏“架构”。
4. **并发数 N 的甜点**：N 太小 u 低，N 太大排队和页缓冲冲突上升。🧮 U=1024、每查询在途 W≈8，N≈128–256 个查询/栈就能让每个 bank 有活干。这个规模刚好适合 GPU 批处理（可以参考 GPU 图 ANN 如 CAGRA 的批量搜索方式，待读）。
5. **页级图（PageANN 思路）**：既然 sense 是单位成本，干脆让“一页 = 图上一个超级节点”，一跳展开一页里的所有节点，跳数和 η 同时改善。代价是图质量。→ PageANN 在待读清单里，应该优先读。
6. **参数不确定性**：U、tR、bank 内是否多 plane、缓冲替换策略都未定（✅ 规范未给）。所有结论要在参数扫描下成立，不能只在一组参数下成立。

## 5. 建议的推进顺序

| 步骤 | 内容 | 回答什么问题 |
|---|---|---|
| 1 | **trace 驱动的最小模拟器**：用 DiskANN（Vamana）在 SIFT/DEEP 1M–10M 上跑 beam search，记录每个查询每跳读了哪些节点；按 OCP 规则回放（页号 → bank、2 缓冲、同 bank 保序、tR 可调） | 现状到底多差：u、η、ρ、页缓冲命中率随 N 的变化 |
| 2 | 在模拟器里逐个加：HBM 热点缓存 → decoupled → harvesting → 主机侧队列 + 优先级 → 副本 → 着色 | 每个部件各贡献多少（消融），先做便宜的 |
| 3 | 推测读策略对比：PipeANN 式固定/动态 W vs “只填空闲” | 洞察 3 是否成立 |
| 4 | 选出收益最大的两三个部件，换到 HBFSim / HBF-EventLab 上做更细的验证 | 结论在更真实的模型下是否保持 |

第 1 步不依赖任何新想法，**也是唯一能把“37% 撞车”“缓冲命中≈0”这些推算变成数据的办法**，建议先做。

## 6. 补读 PageANN、CAGRA 之后的更新

### 6.1 三个新判断
1. **页节点图（PageANN）把问题 1 变成一个干净的图论问题** 💡
   在页图里，“一个页的邻居页”就是读完它之后下一轮的候选页。所以“同轮候选不撞 bank” = **页图的距离-2 着色**（同一页的任意两个邻居颜色不同），颜色数 = 并行单元数，颜色 = 页号 mod（bank 数）（✅ OCP §4.6）。完全无冲突不一定可行（页度数可能上百），但“最小化冲突着色”是一个可以写清楚、可以评估的目标。比 §3 里“Starling 分页后再着色”更直接。
2. **随机入口（CAGRA）可以直接消掉热点入口** 💡
   CAGRA 证明不用固定 medoid 也能搜得好：随机采样一批点、用距离挑起点。HBF 上用 HBM 里的 PQ 码比较这些随机点，不产生额外 sense。入口负载被均匀撒开，**热点 bank 和读干扰**（根因 ③）一起缓解。待验证的是跳数会增加多少。
3. **页节点图缓解了问题 1，但把压力推给问题 2** 🧮
   页越“胖”，每跳要读的页越少，单查询在途量越小，吃满 HBF 并行就越依赖多查询并发。CAGRA 的执行模型（一批上万个查询，每查询一个 CTA）正好提供这种并发，但它的**步调一致迭代**在 HBF 上会被最慢的 bank 拖住，需要改成异步，或由调度器保证每轮均衡。

### 6.2 更新后的系统形态（草案）
```
GPU：CAGRA 式批量搜索（上千查询并发） + 异步展开（读到一页处理一页）
HBM：PQ 码（随机入口 + 候选排序）、热点页缓存、查询状态
调度器：每 bank 队列、关键 > 推测、同页合并（§2 洞察 2、3）
HBF：页节点图（PageANN 式自包含页），页号按距离-2 着色分配 bank；热点页多副本
```

### 6.3 新增实验维度
- 节点图 vs 页节点图：sense 次数、跳数、单查询在途量
- 固定入口 vs 随机入口：热点 bank 负载、跳数变化
- 页图着色 vs 默认顺序编号：同轮 bank 冲突率、ρ
- 步调一致 vs 异步迭代：在 bank 冲突下的尾延迟
