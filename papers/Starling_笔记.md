# Starling 精读笔记（SIGMOD'24, arXiv 2401.02116, 浙大 + Zilliz）

PDF：`papers/Starling_arXiv2401.02116.pdf`　代码：https://github.com/zilliztech/starling

## 一句话
**重新排列节点在磁盘上的位置，让一个 4 KB 块里尽量装“互为邻居”的点。一次读块就能顺带拿到几个有用的点**，再加上内存导航图缩短路径。在单 segment（≤2 GB 内存、≤10 GB 盘）场景下，相同精度时吞吐最高提升 43.9 倍、延迟降低 98%（相对 DiskANN）。

## 它发现的两个问题（§3.1）
| 问题 | 原因 | 数字 |
|---|---|---|
| ① 数据局部性差 | DiskANN 按 ID 连续放块，同块的点在图上互不相关 | 一次读块 **94% 的点没用**；I/O 时间占总搜索时间的 92.5% |
| ② 搜索路径长 | 固定入口点离 query 很远 | 千万级数据集的路径可达上百跳 |

## 核心定义
- 一个点占 γ KB（向量 + 邻居数 + 最多 Λ 个邻居 ID），一块 η KB → 每块最多 ε = ⌊η/γ⌋ 个点（一个点不跨块）。
  - 例：BIGANN（128 维 uint8）、Λ=31、4 KB 块 → γ ≈ 256 B，ε = 16。真实数据集的 ε 大约是 10。
- **Overlap Ratio**：OR(u) = |B(u) ∩ N(u)| / (|B(u)| − 1)，即同块其他点中有多少是 u 的邻居。OR(G) 是所有点的平均值。
  - DiskANN 原布局 OR(G) ≈ 0；Starling 重排后为 **0.3–0.6**。
- **Block Shuffling**：在“每块 ≤ε 个点、每个点只存一份”的约束下最大化 OR(G)。
  - **定理 4.1：NP-hard，而且没有有限近似比的多项式近似算法**（除非 P=NP）。

## 三个启发式算法
| 算法 | 做法 | 复杂度 | 备注 |
|---|---|---|---|
| BNP | 按 ID 扫描，把 u 和它尚未分配的邻居塞进当前块 | O(\|V\|) | 最快，效果最差 |
| **BNF**（推荐） | 以 BNP 为初值迭代：每个点放到“上一轮中装了它最多邻居、且未满”的块 | O(β·o·\|V\|) | 只占建图时间的 3–10%，性价比最好 |
| BNS | 两个块之间交换 OR 最低的点，只在总 OR 上升时才换 | O(β·o³·ε·\|V\|) | 保证 OR 单调不降，效果最好但最慢 |

注：作者试过通用图划分（KGGGP），OR 比 BNF 低 40%。原因是向量图约有 50% 的长边，出度均匀，不像社交图那样天然成簇。

## 搜索侧（§5）
1. **内存导航图**：采样不到 10% 的点建小图，给出靠近 query 的动态入口点。同召回下 I/O 减少约 20%。
2. **Block search**：读回一块后，对块内**所有点**算精确距离；按距离排序后，只展开前 (ε−1)·σ 个点的邻居（σ=0.3 最优，即 block pruning）。
3. **I/O 与计算流水**：发出下一次读块的同时，计算上一块里的非目标点。比 PipeANN 弱，只重叠一步。
4. **PQ 距离做路由**：邻居 ID 数是每块点数的好几倍，块内装不下所有邻居，所以用内存里的 PQ 码决定下一跳。

## 结果要点
- I/O 时间占比从 92.5% 降到 57.7%。
- 和 PipeANN 对比（PipeANN 论文 §5.2）：0.99 召回时，Starling 每次查询的 I/O 只有 PipeANN 的约 1/2，吞吐更高；但延迟更高（每次只发 W=4 个，且一步一步走）。

## 和 HBF 的关系（我们的解读）—— 问题 1 的出发点
1. **Starling 的代价模型是“读一块 = 固定成本”，只追求读块次数最少。** 它完全不管块放在哪个 die 或 bank，这部分由 SSD 的 FTL 打散处理。到了 HBF，“哪些块落在同一 bank”直接决定能否并行（见 03 文档 §1.2 根因 ①）。
2. **Starling 每次传回整块 4 KB，再在主机上筛选块内的点。** HBF 可以只传 64 B 的倍数，就出现了新的取舍：
   - 传整页，等同于把页“缓存”到 HBM：省掉以后重新 sense，但费 channel 带宽；
   - 只传目标点（约 256 B）：省带宽，但想再取同页其他点时，页可能已经被挤出那 2 个页缓冲。
   Starling 的 OR 只有 0.3–0.6，也就是说**整页传输中约一半是浪费**。在 HBF 上值不值，需要量化。
3. **OR 的目标只看“块内有多少邻居”，不看“同一轮被并发读的块是否在同一 bank”。** 我们需要的是一个改写过的目标：块内重叠（减少 sense 次数）+ 同轮候选块的 bank 分散度（避免冲突）。这正是“page + channel + bank 联合排列”的形式化入口。
4. 问题本身已经 NP-hard 且没有近似算法。加入 bank 维度只会更难，**所以方案大概率是启发式的**，比如在 BNF 之后再做一次 bank 着色或分配。
5. 重排的开销：十亿规模下时间和内存都很大，PipeANN 因此没有采用。我们若做联合排列，**构建开销也必须控制**。
