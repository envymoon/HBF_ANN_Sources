# PageANN 精读笔记（arXiv 2509.25487v2，2025-10，UT Dallas / Rutgers）

PDF：`papers/PageANN_arXiv2509.25487.pdf`　代码：https://github.com/Dingyi-Kang/PageANN

## 一句话
**把图的“节点”从单个向量换成一整页（page node）：一跳 = 读一页 = 一次 I/O。** 页里放若干相似向量、这一页对外的邻居 ID、以及这些邻居的压缩向量，所以下一跳去哪只看当前页就能决定。

## 1. 它指出的三个问题（§3）
1. **跳数少 ≠ I/O 少**：Vamana 降低了图直径，但逻辑上的一跳和物理上的一次读不对应，布局差的时候 I/O 路径更长。
2. **I/O 粒度错配**：SIFT 一个向量 128 B，SSD 最少读一页 4 KB。表 1 的读放大（SIFT100M / SPACEV100M / DEEP100M）：DiskANN 18.3 / 20.1 / 8.0，Starling 1.71 / 1.95 / 1.28，PipeANN 同 DiskANN，SPANN 2.0。
3. **内存索引开销大**：PQ 码、路由图都要常驻内存，内存比例从 50% 降到 10% 时延迟上升 3 倍以上；SPANN 低于 30% 跑不起来。

## 2. 设计（§4）
### 2.1 页节点图的构建（Alg.1）
- 以 Vamana 图为底图。取一个未分组的向量 v，在它 **h 跳内**未分组的邻居里选最近的 n−1 个，组成一页。凑不满时**用任意剩余向量填满**（第 9–11 行）。
- 页的外部邻居 = 页内所有向量的邻居并集，去掉页内的、去重。
- 每页能放的向量数由页大小、邻居数、压缩向量数共同决定（公式见 §4.2）。

### 2.2 页内布局（图 5）
每页三段：① 页内向量的全精度值（算精确距离）；② 页的邻居 ID；③ **邻居的压缩向量**（决定下一跳）。
→ 下一跳只依赖当前页，不需要回内存查 PQ 码；每个压缩向量在内存和磁盘之间只存一份。

### 2.3 内存管理（§4.3）
- **轻量路由**：采样部分向量做随机超平面哈希（LSH 风格），按汉明距离找入口候选。
- **内存-磁盘协调**：内存少时，邻居压缩向量都放在页里；内存多时，压缩向量放内存，页里腾出空间多放向量 → 页节点图更小、路径更短。
- 预热找出热门页缓存。

### 2.4 搜索（Alg.2）
- 每跳从候选里按 PQ 距离取最近的未访问向量，换算成页号，**同页去重**，凑满 b 个页（实验 b=5）后批量读。
- 读回的页：页内所有向量算精确距离进结果集；页邻居用压缩距离进候选集。
- 用 Linux AIO 把计算和 I/O 重叠。

## 3. 结果（§6）
- 100M 数据集、30% 内存：R@10=0.9 时，吞吐比次优方案高 85% 以上，**平均 I/O 少 46%**（SIFT100M：PageANN 85 次 vs DiskANN 187、Starling 158）。
- 十亿级：R@10=0.9 吞吐提升 1.9–3.8 倍；R@10=0.95 时提升 2.2–7.5 倍。
- 内存几乎为 0（0.05 GB，即数据集的 0.05%）也能达到 R@10=0.9。
- 16 线程内近线性扩展；构图时间比 DiskANN 多约 30–40%。

## 4. 对我们的意义

**1. “sense 是计价单位”的想法，它在 SSD 上已经验证过了。** 一跳 = 一页，η（每次 sense 用上的节点数）是被结构性保证的，而不是靠布局碰运气（Starling 只有 0.3–0.6 的重叠率）。docs/03 里“跳数 × tR”的延迟下限，在页节点图上就是“页跳数 × tR”，这个数比节点跳数小。

**2. ⭐ 页节点图让 bank 分配变成一个干净的图问题。** 这是我读完最大的收获：
- 在页节点图里，**一个页的邻居页 = 读完这一页后下一轮可能同时去读的那批页**。
- 所以“同一轮候选不撞 bank”就是：**任何一个页的所有邻居页，分到不同的 bank**。这在图论里叫**距离-2 着色**（distance-2 coloring）：页图上距离 ≤ 2 的两个页颜色不同。
- 颜色数 = 并行单元数（256–1024）；`页号 mod 16` 的确定映射让“分配颜色”就等于“分配页号”（✅ OCP §4.6）。
- 页的度数可能很大（n 个向量的邻居并集），完全无冲突的着色未必存在，但**最小化冲突**的启发式着色是可做的，而且比在节点图上做（Starling 那样先分页、再考虑 bank）更直接。

**3. 自包含页适合 HBF 的容量分层。** 下一跳的决策信息（邻居 ID + 压缩向量）都在页里，HBM 里不必放全部 PQ 码。HBM 容量（每栈约 64 GB）可以留给热点页缓存和查询状态。代价是同一个压缩向量可能出现在多页里（它用合并来控制）。

**4. 它没解决的，正是我们的问题。**
- 只在 CPU + 单块 SSD、16 线程、固定 b=5 下评估。**没有考虑高并发时页之间的 bank 冲突**，也没有页缓冲问题（SSD 读回整页留在主机内存）。
- 页填不满时用任意向量补（Alg.1 第 9–11 行），这些“垃圾填充”会拉低 η。
- 入口点来自 LSH 路由。在高并发下，热门入口页仍然会形成热点 bank。

**5. 一个新问题（待讨论）**：页节点图的 b（每跳读几页）相当于 W。页越“胖”，每跳需要的页越少，单查询在途量越小，对 HBF 的并行就越要依赖多查询。也就是说，**页节点图把问题 1 缓解了，但把压力更多地推给了问题 2（多查询调度）。**
