# PipeANN 精读笔记（OSDI'25, Hao Guo & Youyou Lu, 清华）

PDF：`papers/PipeANN_OSDI25.pdf`　代码：https://github.com/thustorage/PipeANN

## 一句话
**best-first 搜索不一定要严格地“读完一批、算完、再读下一批”。** 下一步读谁只看内存里的候选池就能决定，所以 I/O 可以一直发、计算可以和 I/O 重叠。结果：延迟只有 DiskANN 的 35%（十亿规模），相当于内存版 Vamana 的 1.14–2.02 倍。

## 它发现的两个问题（§2.2，都是 SSD 上实测）
| 问题 | 现象 | 数字 |
|---|---|---|
| ① 计算和 I/O 严格交替 | 每一步要等上一步的 I/O 和计算都完成 | W=1 时计算只占 I/O 时间的 9.5%；W=8 时占 45.6%。**这些计算本来可以藏进 I/O 等待里** |
| ② 每一步同步等全部 I/O | 一批里只要有一个慢 I/O，整批都要等它 | 管线利用率：W=8 时 76%，W=32 时只有 58%。原因是 **SSD 延迟有抖动** |

## 关键观察：伪依赖（pseudo-dependency）
- 下一个要读的节点 = 候选池里“最近、还没读过”的那个。候选池在内存里，**不需要等在途 I/O 返回就能决定**。
- 图上每个点有多条入边，也就有多条搜索路径。所以偏离严格 best-first 不会导致搜不到，**只是多走几步、多读几次**。

## 算法（Algorithm 2 简化版）
```
W = 4；先在内存小图里找入口点（approach phase 加速）
循环：
  if 在途 I/O 数 < W：发出候选池中最近且未读的 1 个节点
  从“已读回但未展开”的集合 U 里取最近的 1 个，展开它（用 PQ 距离更新候选池）
  轮询完成的 I/O，放入 U
  动态调整 W
```

## 三个关键设计
1. **两阶段 + 动态 W**
   - Approach 阶段（向目标靠近）：猜错率高，W 小（固定 4），并用内存小图（1% 采样，出度 32）缩短这段。
   - Converge 阶段（在目标附近收拢）：候选池里有大量“没验证过的 top-k 邻居”，猜错率低，W 可以大。
   - 何时切换：估计的已召回数 n_v ≥ 5。之后每当“读回的节点仍在候选池中的比例 > 0.9”时 W += 1，上限 32。
2. **限速补发**：多个 I/O 同时完成时，不一次补满管线，而是 **“展开 1 个 → 发 1 个”交替进行**。这样第 n 个 I/O 最多缺 W 个节点的邻居信息，决策更准；I/O 次数降到 91.8%，吞吐 ×1.08。
3. **工程细节**：io_uring + SQ polling；第一个 I/O（约 50 µs）和 PQ 表初始化重叠执行。

## 代价（对我们很重要）
- **推测式 I/O = I/O 浪费**。W=32 的 I/O 次数是 W=8 的 2.44 倍；W=8 时 PipeSearch 的 I/O 次数是 best-first 的 1.34 倍。
- 吞吐：低召回（0.8）时比理想 best-first（W=1、多查询交错）低 17–34%；召回 0.95 时只低 5–15%。
- 在 0.99 召回时，PipeANN 每次查询的 I/O 是 Starling 的 1.94 倍，**吞吐反而比 Starling 低**（SSD 带宽被打满）。作者指出它和 Starling 的布局是正交的，可以组合，但没做（十亿规模下重排太贵）。

## 和 HBF 的关系（我们的解读）
1. 论文 §4.5 自己写了：机制适用于“µs 级延迟 + 并行 I/O”的其他介质（RDMA、CXL）。**HBF 的 tR 也在 µs 级（1–20 µs），和每条记录的计算时间同一量级 → PipeSearch 的前提成立。**
2. **SSD 上 I/O 浪费的代价是带宽和 IOPS，HBF 上变成了 bank 占用。** HBF 带宽很大，多读一些不太可怕，但每个推测读都会占用某个 bank 一个 tR，挡住排在它后面的关键读（见 03 文档 问题 2 根因 ①）。
3. PipeANN 只控制 **“何时发、发多少（W）”**。它在 SSD 上遇到的“延迟抖动”，在 HBF 上主要来自 **bank 冲突和页缓冲命中/未命中**，而这些可以通过调度来控制。→ 这就是问题 2 的切入点：**在 W 之外，再加上“发哪个、按什么顺序、发到哪个 bank”。**
4. PipeANN 的吞吐测试只开了 56 线程（每线程 1 个查询），SSD 上就够了。HBF 要几千个在途请求（01 文档 Little 定律），**单查询 W≤32 远远不够，必须多查询并发**，这时跨查询的 bank 冲突就成了 PipeANN 没碰过的新问题。
