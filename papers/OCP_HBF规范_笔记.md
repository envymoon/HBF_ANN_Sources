## 1. 结构与容量（§4、§4.2）

```
HBF 栈 = Base die（底层逻辑） + Core die（NAND 堆叠） + TSV
 └─ 16 个 Host Channel（UCIe），彼此独立、异步，互相不能访问对方的数据
     └─（每个 channel 可再分 1/2/4 个虚拟 AXI 口，容量均分）
     └─ 若干 Core die（每个 channel 1–16 个，寄存器 NCDU 可读）
         └─ 每 die 16 个 bank（§4.6 例子）
             └─ 每 bank 2 个 4 KiB 缓存缓冲（cache buffer，寄存器 NCBB，默认 2，其余取值保留）
```

| 参数 | 值 | 出处 |
|---|---|---|
| 页大小 | 4 KiB | §4.1 |
| 读粒度 | 64 B 到 4 KiB，按 64 B 倍数、64 B 对齐，**不跨 4 KiB 页** | §4.1 |
| 写粒度 | 只能 4 KiB，地址 4 KiB 对齐 | §4.1 |
| 每 channel 带宽 | 64 bit × 32 GT/s = 256 GB/s（原始）；扣除 AXI 开销 75% 后 | 表 2 |
| 每栈有效带宽 | 3 档：0.384 / 1.536 / 3.072 TB/s（UCIe 8 / 16 / 32 GT/s） | 表 4 |
| 每栈容量 | 512 GiB | 表 3 |
| **tR（读页时间）** | **规范没有给出** | 全文搜索确认 |

⚠️ **规范内部数字不一致**：表 3 写“每栈 16 个 die、每 channel 16 个 bank”（即每栈 256 bank），§4.6 的例子却是“每 channel 4 die × 16 bank = 64 bank”（每栈 1024 bank）。§11.1.1 又说并行单元 N 是 “bank 或 plane 数”，“N 的最大值 = 每 die 的 plane 数 × 每 channel 的 die 数”。
→ **真实的并行单元数量（bank/plane）由产品决定，要读寄存器才知道。** 用 3 TB/s 反推（见第 6 节）：每栈需要约 750–3000 个能同时感测的单元，表 3 的 256 个不够。所以“bank”里大概率还有多个 plane，或者 tR 远小于 4 µs。

## 2. 地址映射（§4.6、§11.1）—— 问题 1 的关键

### 2.1 两层映射
1. **全局地址 → channel**：由**主机软件**决定。交织粒度可以配置为 64 B、128 B……4 KiB，最大到整个 channel 容量（图 3）。
   - `channel = (G_Addr / 粒度) mod 16`
   - `local_addr = 粒度 × ⌊G_Addr / (粒度 × 16)⌋ + (G_Addr mod 粒度)`
2. **channel 内本地地址 → die / bank / block**：由 **Base die** 负责，主机“不需要知道”。但规范给了推荐的条带化方式，**主机也可以从配置寄存器读出映射**。
   - 设备逻辑单元（4 KiB）= 本地地址（以 64 B 为单位）>> 6
   - **逻辑单元号的最低 4 位 = bank 号，接下来 2 位 = die 号**

### 2.2 图 4 的条带化：**连续的 4 KiB 页轮流落到不同 bank**
```
逻辑页  0..15  → Die0 的 B0..B15
逻辑页 16..31  → Die1 的 B0..B15（另一个 core-die channel）
逻辑页 32..47  → Die2 的 B0..B15
逻辑页 48..63  → Die3 的 B0..B15
逻辑页 64..    → 回到 Die0 B0 ……
```
- **同一个 bank 里相邻的两页，地址相差 64 页（256 KiB）**。
- 一个 NAND block 内的页，地址按 `L2, L2+R5, L2+2·R5, …` 排列（§5.7，R5 是条带宽度）。

### 2.3 对 ANN 的直接含义
- ✅ **bank 是可预测、可控制的**：在默认条带化下，`bank = 页号 mod 16`，`die = (页号 / 16) mod 4`。**软件选定节点放在哪个页号，就同时选定了它在哪个 channel、哪个 bank。** 所以“page + channel + bank 联合排列”在硬件上可以实现，不需要新硬件。
- ✅ **修正我们之前的推测**：之前担心“相邻页落在同一 bank”。按默认映射，**相邻页恰好在不同 bank**。真正的问题是：布局算法（如 Starling）分配页号时完全不考虑 `页号 mod 64` 和 channel，于是 bank 对图结构来说相当于**随机分配**。同一轮的候选会随机撞到同一个 bank，入口点所在的 bank 也会成为热点。
- ⚠️ **全局交织粒度必须 ≥ 4 KiB**：如果用 64 B 交织，一个 4 KiB 节点页会被拆到 16 个 channel 上。读一个节点就要在 16 个 bank 上各感测一次，浪费 16 倍的 sense。LLM 权重顺序读不怕这个，图 ANN 很怕。

## 3. 读协议（§5.2.4、§5.3）—— 问题 2 的关键

逐条原文要点：
1. 读请求都是 64 B 粒度。要读整个 4 KiB，可以发 64 条不同 AXI ID 的命令，或者发一条 burst（长度 0–63）。
2. **乱序规则**：AXI ID 不同的请求可以乱序完成，ID 相同的保持顺序。AXI ID 宽 14 bit。
3. **缓冲命中**：只要不违反顺序约束，立即返回。
4. **缓冲未命中**：**要等该 bank 上前一个读完成，才触发 sense**。
5. **同一 bank 的 sense 严格按顺序执行**（“strict ordering for sense requests … within the same bank”）。
6. **每个 bank 2 个缓存缓冲。规范建议：先把第一页读完，再发会挤掉它的第三个页地址。**
7. **普通读 vs 批量读（Batch Read）**：
   - 普通读：Base die 会**攒一段时间（定时器）**，再“最优地”调度到 Core die。
   - 批量读：AXI user 位置 1。Base die **不等定时器**，把到目前为止收到的读立刻一起调度，直到遇到一个普通读为止，视为批次结束。
8. **在途命令上限（MOCS 寄存器）**：每个 channel 256 到 16384 条，由产品决定，主机可选。
9. channel 之间不保序；**所有 channel 同时读时性能最高**（§11.2.1）。

→ 对问题 2 的含义：
- **一旦把请求发出去，同一 bank 里的顺序就固定了**（规则 5）。主机想要优先级，只能在**发出之前**排好：先发关键请求，推测请求要么后发，要么发到空闲的 bank。这从规范层面证实了“队头阻塞”是真实存在的。
- **批量读提示**相当于一个现成的调度接口：主机可以把“一轮里互不冲突的请求”打包成一个批次立刻发出；也可以不加提示，让 Base die 去攒。后者的代价是定时器带来的额外延迟。
- 规则 6 与“同页请求要挨着发”的结论（03 文档问题 2 根因 ③）完全一致。

## 4. Scratchpad SRAM（§4.1、§5.3.3、§11.3）—— 可选，但对我们很有用
- Base die 上每个 channel 都有一块 SRAM，**延迟和 L3 cache 同一量级**，读写都是高优先级、走满 UCIe 带宽，由主机自己管理，掉电丢失。
- 粒度 64 B，不需要攒满 4 KiB。
- → **适合放热点节点**（入口点、上层导航图、枢纽节点）。它比放 HBM 离 HBF 更近，而且不占 HBM 容量。HBFlex 假设的容量是每栈 40 MB。

## 5. 可靠性约束（§9、§11.4、§11.5）—— 以前没意识到的坑
| 约束 | 内容 | 对 ANN 的影响 |
|---|---|---|
| **读干扰（read disturb）** | 每个 block 被读 X 次（由产品决定）后，**主机必须刷新**（重写）该 block。Base die 会统计每个 block 的读次数，超阈值时在返回状态里报 CECC/UECC | **热点节点（入口点、枢纽）被每个查询都读 → 所在 block 很快需要重写**。所以把热点挪到 SRAM/HBM 或做多副本，**不只是为了性能，也是为了寿命和可用性** |
| 数据保持 | 上电状态下 85 °C 时只保证 24 小时；需要每 24–48 小时刷新一次 | 整个索引要周期性重写。刷新时**不要和读同时落在同一个 die**，否则读延迟会上升 |
| 写 | 只能写 4 KiB，**同一 NAND block 内必须顺序写**；没有 GC；写 page-0 时自动擦除 | 索引更新 = 整块重写，“怕写”的结论得到确认 |
| 温度 | 正常 → 轻度降频（变慢）→ 重度（停止 IO、反压）→ 关机 | 持续高并发可能触发降频 |

## 6. 用规范数字算一笔账：**真正的资源是“sense 次数/秒”，不是带宽**

每个 bank 每 tR 只能完成一次 sense。所以：
```
最大 sense 速率 = 并行单元数 / tR
满页带宽       = sense 速率 × 4 KiB
图 ANN 实际有用带宽 = sense 速率 × 每次真正用到的字节数（一个节点约 256 B–1 KiB）
```
| 并行单元/栈 | tR | sense/s | 满页带宽 | 只用 512 B 时 |
|---|---|---|---|---|
| 256（表 3） | 4 µs | 64 M | 0.26 TB/s | 33 GB/s |
| 1024（§4.6 例子） | 4 µs | 256 M | 1.05 TB/s | 131 GB/s |
| 1024 | 1 µs | 1024 M | 4.2 TB/s | 524 GB/s |

（对照：HBFlex 的“业界配置”是 512 plane/栈、tR 4 µs → 512×4 KiB/4 µs ≈ 524 GB/s，和它设的 488 GB/s 一致。说明大家都按“带宽 = plane 数 × 页大小 / tR”来建模。）

→ **结论：对图 ANN 来说，“3 TB/s”基本是虚的。** 每次 sense 只用到几百字节，瓶颈在 **sense 速率**（bank 时间）。所以：
- 衡量一个布局的好坏，看的是 **每次 sense 能用上多少字节 / 多少个有用节点**。Starling 那类 co-location 在这里的价值比在 SSD 上更大。
- 衡量一个调度的好坏，看的是 **bank 时间有没有被浪费**：空等、被推测读占用、同 bank 冲突排队。
- 单栈理论上限（1024 单元、4 µs、每查询约 100 次 sense）：约 256 M / 100 ≈ **250 万 QPS**。实际能达到多少，取决于冲突和热点能控制到什么程度。

## 7. 已解决 / 仍待解决（对照 03 文档 §4）
| 问题 | 结论 |
|---|---|
| 地址 → channel/die/bank 的映射 | ✅ 全局 → channel 由主机配置；channel 内由 Base die 映射，**默认按 4 KiB 页轮流分配 bank → die**，主机可从寄存器读出 |

| Base die 定时器时长、调度策略 | ❓ 产品决定（TMR 寄存器） |
