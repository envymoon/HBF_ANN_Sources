# HBFlex 精读笔记（arXiv 2609.18675, 2026-09, 北大 / 港科大 / 阿里）

PDF：`papers/HBFlex_arXiv2609.18675.pdf`

## 一句话
**LLM 的 KV cache 是细粒度、动态的，HBF 的并行却是“粗粒度、按 plane 的”。** HBFlex 用三招弥合二者：
- 按 plane 均衡放置 + 运行时读均衡；
- 写回时找足够长的计算窗口；
- 按生命周期打包，减少 GC。

它取消了 HBM，整个封装都用 HBF。相比 FlashAccel 吞吐提升 1.58 倍，相比 H3 提升 3.30 倍。

## 硬件建模（“业界提供”的配置，可以作为我们的默认参数）
| 参数 | 值 |
|---|---|
| 每栈 | 16 die × 32 plane = **512 plane**（6 栈共 3072 plane） |
| 每 plane | 512 个 block × 512 页 × 4 KiB |
| **读延迟 / 写延迟** | **4 µs / 75 µs（写不可抢占）** |
| 带宽 | 读 488 GB/s/栈，写 27.2 GB/s/栈 |
| Base die SRAM | 40 MB/栈（3 nm 工艺约 8 mm²，占 base die 的 6.7%） |

注：它的层级是 die → plane，没有用 OCP 的 “bank” 这个词，**并行单元就是 plane**。

## 和我们问题 1 最像的部分：Read Imbalance（§3.1）
- **完成时间由最忙的那个 plane 决定**，因为同一 plane 上的读是串行的。
- 不均衡度：**ρ = 最大 plane 负载 / 平均负载**。
- 两类不均衡：
  1. **放置不均衡（placement imbalance）**：数据存放本身就不均。即使当初放均匀了，请求结束、重新激活之后也会变得不均。
  2. **访问不均衡（access imbalance）**：即使存放均匀，**某一次访问只取一个子集，这个子集也可能扎堆在少数 plane 上**，于是需要多“轮”读（read waves）。
  - 例：一次读 12 MiB = 3072 页，理想情况下每个 plane 恰好 1 页；一旦撞车，就要多读几轮。
- 加大 KV 页（让一个逻辑页跨多个 plane）可以减少撞车，但会削弱前缀复用。**逻辑粒度和物理并行粒度之间存在取舍。**
  → 对应到 ANN：**一个节点在一页内（利于少 sense），和一轮候选分散在不同 plane（利于并行）**，正是这个取舍。

## 它的解法（§5.2），可以直接借鉴到图 ANN
| HBFlex 机制 | 做法 | 映射到图 ANN |
|---|---|---|
| **Plane Group 条带化** | plane 分组，相邻物理页在组内跨 plane 条带化；逻辑分配粒度不变 | 节点分页之后，再决定页落在哪个 bank（利用 OCP 的 `页号 mod 16` 规则） |
| **热点前缀多副本** | 系统提示词等共享前缀复制到多个 PG；运行时把读重定向到负载轻的副本 | **入口点、导航层节点复制到多个 bank**，查询从最空闲的副本读。也能缓解 read disturb（见 OCP 笔记 §5） |
| **热点 plane 卸载到 SRAM** | 只把最热的 10% plane 上多出来的页放进 base-die SRAM，每栈约 6–12 MB；超过 10% 之后收益很快变平 | 热点节点放进 OCP scratchpad SRAM |
| **按放置位置调度** | 每一轮贪心选择能覆盖最多不同 plane 的 KV 块；相近的情况下优先选同一请求的块，以复用 query | **多查询调度**：从所有查询的候选里挑一组 bank 不冲突的请求一起发 |

**效果**：读轮数放大（实际读轮数 / 理想最少轮数）从 5.97 倍降到 3.95 倍（均衡放置），再降到 2.25 倍（加上运行时均衡）。吞吐提升主要来自读优化（约 4.1–4.3 倍）；写和 GC 优化对吞吐贡献很小，主要是延长寿命。

## 写和 GC（§3.2–3.3、§5.3–5.4），与 ANN 关系较远，简记
- 一次写占用 plane 75 µs 且不可抢占，会挡住后面的读。HBFlex 先把 KV 攒在 SRAM，等到 prefill 计算窗口足够长时再写。
- KV 寿命混杂导致 GC 写放大约 30 倍；按生命周期打包、延迟回收后降到约 1.04 倍。
- → 对 ANN 的启发：**索引更新（插入/删除）的写入同样会挡读**，以后做动态索引时需要“找窗口写”。

## 和我们的区别
- KV 访问在一次 attention 调用里**全部已知**（页表给出），可以整体做负载均衡。**图搜索每一跳的访问只有在上一跳完成后才知道**，均衡只能在“一轮候选 + 多查询”的范围内做，而且要和推测读结合。
- 它没有处理页缓冲命中的问题（KV 页基本整页读）。我们的节点只有几百字节，**一次 sense 能否顺带服务多个节点**是 HBFlex 没有碰到的维度。
