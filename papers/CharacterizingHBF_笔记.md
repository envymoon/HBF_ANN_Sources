# Characterizing High Bandwidth Flash for LLM Serving 精读笔记（arXiv 2609.39131v2, 2026-10, UC Berkeley）

PDF：`papers/CharacterizingHBF_arXiv2609.39131.pdf`（10 页）

## 一句话
请求级模拟器 + 多轮 agent 负载，评估 **HBM–HBF–主机 DRAM/SSD 四层存储** 对 LLM 服务的价值，并提出“带缓冲的缓存感知调度”（预留 10% 准入余量，避免新请求把可复用的 KV 挤掉）。HBF 系统比纯 HBM 完成时间缩短 36–88%，估计的 HBF 写寿命从 1.21 年延长到 14.82 年。

**这是系统层面的论文，和图 ANN 没有直接关系**，只在相关工作里把 HAVEN 列为“flash 上的向量检索”。它的价值在于提供了一套 HBF 参数和几条系统设计原则。

## 它假设的 HBF 参数（Table 1，每栈）
| 参数 | HBM | HBF |
|---|---|---|
| 容量 | 24 GB | 375 GB（引自 H3） |
| 读带宽 | 1000 GB/s | 1000 GB/s |
| 写带宽 | 1000 GB/s | **8 GB/s** |
| 读启动延迟 | 0.1 µs | **20 µs** |
| 写启动延迟 | 0.1 µs | **250 µs** |
| 读能耗 | 3.4 pJ/bit | **6.8 pJ/bit（HBM 的 2 倍；H3 报告最高 4 倍）** |
| 写能耗 | 3.4 pJ/bit | 100 pJ/bit |
| P/E 寿命 | — | 100,000（SLC） |

注：表中 HBF 的数字顺序是我按列含义还原的（读启动 20 µs、读能耗 = HBM 的 2 倍都与正文吻合）。**这里的 tR 取 20 µs，是保守端**（HBFlex 取 4 µs，HBFSim 取 20 µs）。

## 对我们有用的点
1. **“写 8 GB/s、读 1000 GB/s”**：读写带宽差约 125 倍，印证 ANN 索引必须是只读为主。
2. **能耗**：HBF 每比特读能耗是 HBM 的 2–4 倍。→ 推测读（白读）不只占用 bank 时间，**也直接增加能耗**。HAVEN 的功耗上限分析与此一致。评价调度方案时可以加一个“每查询能耗”指标。
3. **分层原则：热的在 HBM，冷的在 HBF；激活值这类短命数据不写 HBF**（会很快耗尽寿命）。这支持我们的“导航层/热点放 HBM 或 SRAM，长尾放 HBF”的方向。
4. **“Index-first 放置”**（稀疏注意力：indexer 要扫全部索引数据，所以把索引当作更热的数据留在 HBM，KV 才下沉到 HBF）。→ **和图 ANN 的 PQ 码放 HBM、全精度向量和图放 HBF 是同一个思路**，只是在更细粒度上。
5. **准入控制保护缓存**：限制活跃请求量（b=0.9），防止新请求把可复用状态挤出去，写量降低 69%–92%。→ 对应我们的问题：**多查询并发（为了吃满带宽）会冲掉页缓冲**。同样可以考虑“限制同一 bank 上同时在途的查询数”，宁可少并发，换取页缓冲命中。
6. 它假设 “HBM 缓冲能完全隐藏 HBF 延迟”（H3 架构）。这个假设对图 ANN 不成立，因为我们下一跳读什么要等上一跳。

## 局限
- 模拟器在请求级别，不建模 channel/bank/页缓冲，**对我们的两个问题没有帮助**。
- 写参数主要用“典型 SSD 参数”，作者承认公开的 HBF 写规格有限。
