# CAGRA 精读笔记（arXiv 2308.15136v2，ICDE'24，NVIDIA）

PDF：`papers/CAGRA_arXiv2308.15136.pdf`　代码：RAFT / cuVS 中的 `cagra`

## 一句话
**为 GPU 设计的图 ANN：固定出度的图 + 不分层 + 随机入口 + 每个查询一个 CTA 的批量搜索。** 数据和图全部放在 GPU 显存里；大批量查询下比 HNSW 快 33–77 倍，比其他 GPU 实现快 3.8–8.8 倍；单查询在 95% 召回下比 HNSW 快 3.4–53 倍。

## 1. 图（§III）
- **固定出度 d**（32–80）：GPU 上每个节点的工作量一致，负载均衡；度小反而用不满 CTA 的算力。
- **不分层**：不要 HNSW 那样的上层图，入口直接**随机采样 p×d 个节点**，比较距离后挑起点。GPU 算力充足，这点代价可以忽略。
- 构建：先用 NN-Descent 建 k-NN 图（k = 2d–3d），再做两步优化：
  1. **按“可绕行路径数”重排边**（用排名代替距离，不需要再算距离），保留前 d 条，提高 **2 跳可达节点数**；
  2. **加反向边**，减少强连通分量。各取 d/2 交错合并。
- 优化目标是**可达性**（2 跳能到多少节点、连通性），不是像 Vamana 那样压低直径。

## 2. 搜索（§IV）
- 缓冲 = 内部 top-M 列表 + 候选列表（长度 p×d）。迭代：
  1. 从整个缓冲里选出 top-M；
  2. 取 top-M 中最近的 **p 个**还没当过父节点的点，把它们的 d 个邻居 ID 放入候选列表；
  3. 只给第一次出现的候选算距离（用哈希表记录访问过的节点）。
  直到 top-M 不再变化。
- **Single-CTA 模式**：一个查询一个 CTA，适合大批量（≥ SM 数，例如 100 以上），通常 p=1。哈希表放 shared memory，用“可遗忘哈希表”（定期清空，每查询 ≤ 4 KB）。
- **Multi-CTA 模式**：一个查询多个 CTA，适合小批量或高召回；每个 CTA 的 p=1，共享显存中的哈希表，所以每次迭代展开“CTA 数 × d”个节点。
- **Team（软件切分 warp）**：一个距离计算交给 4–8 个线程，提高 128-bit load 的利用率。
- **瓶颈是显存带宽**：大批量、高维时内核受显存带宽限制；改用 FP16 存向量能提升吞吐且基本不降召回。
- 数据超出显存时，作者只提到“多 GPU 分片或 PQ 压缩”，**没有涉及外存**。

## 3. 对我们的意义

**1. 它提供了我们需要的“并发度来源”。** docs/03 根因 ④ 说：单查询在途量太小，HBF 要靠几百到上千个查询同时跑。CAGRA 的执行模型正是这样：**一个批次上万个查询，每个查询一个 CTA**。HBF 挂在 GPU 旁边，自然的系统形态就是“CAGRA 式批量搜索 + 图数据放 HBF”。

**2. ⭐ “随机入口”可以直接消掉热点入口。** 根因 ③：所有查询都从 medoid 出发，前几跳的页成为热点 bank，还会触发读干扰（✅ OCP §11.5）。CAGRA 证明了**不用固定入口也能搜得好**：随机采样 p×d 个点，比距离挑起点。
- 在 HBF 上，比较这些随机点要用 HBM 里的 PQ 码（不然就是一批随机读）。
- 效果：入口负载被均匀撒到全部页和 bank 上，热点和读干扰两个问题一起缓解。代价是可能多走几跳，需要实验验证。

**3. 固定出度 = 每个节点的数据定长 = 每轮需求可预测。** 节点定长让“ID → 页号 → bank”可以直接算（和 DiskANN 一样）；每次迭代每个查询展开 p×d 个邻居，工作量一致，便于调度器预估每轮 bank 需求。

**4. 迭代是“步调一致”的，这在 HBF 上是个隐患。** CAGRA 一次迭代展开、算距离、更新 top-M，在显存里很快。如果邻居表要从 HBF 读，一个查询要等它这一轮所有读都回来；**一轮的耗时由最慢的 bank 决定**。批量越大，越容易有某个 bank 被撞多次。→ 需要异步（读到一个处理一个，类似 PipeANN）或者调度器保证每轮均衡。

**5. 显存带宽是 CAGRA 的瓶颈；换成 HBF 后瓶颈变成 sense 速率。** 🧮 显存几 TB/s，读一个 96 维 FP32 向量 384 B；HBF 每次 sense 要 tR（µs 级）。**计算资源会大量空闲**，所以可以用算力换 I/O：更大的 d、更多随机入口、更多推测距离计算（用 HBM 里的 PQ 码），只要能减少 sense 次数都值得。

**6. 可遗忘哈希表在 HBF 上要小心。** 显存里重复访问只是多算一次距离；在 HBF 上，**重复访问可能是一次额外的 sense**。访问记录不能随便清。

**7. 图的优化目标值得对比。** CAGRA 优化“2 跳可达节点数”（展开更宽），Vamana 优化“直径”（跳数更少）。HBF 上延迟 ≈ 跳数 × tR，宽度可以靠并行吸收，所以 **Vamana 式少跳数、CAGRA 式宽展开**哪种更适合，取决于 bank 冲突能被控制到什么程度。这可以作为实验维度。
